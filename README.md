# repeater-db
Database with REST API for Amateur Radio repeaters, digipeaters and beacons.

This repository is licensed under the Apache 2.0 license.

### Import schema
Note: vhf_schema.sql was generated using "pg_dump -s".

Changes to an existing database are in `postgres/migrations/`; `vhf_schema.sql` already
contains them. They are named `<date>_<nn>_<what>.sql` (e.g. `2026-11-02_03_oelink_status.sql`):
the date they were written and a two-digit number counting up within that day (01-99), so
sorting the file names gives the order to apply them in (`psql vhf -f <file>`, one after the
other). A new migration gets today's date and the next free number of that day.

Owner of the schema objects is the role `vhf_owner` (no login); admins such as `dz` are
members of it (`GRANT vhf_owner TO dz`). So that new objects belong to it too, a migration
starts with `SET ROLE vhf_owner;` (after `BEGIN;`), unless it has to run as postgres
(creating roles). `api.user_login()` has its own minimal owner `vhf_login_writer`, see
`postgres/migrations/2026-11-02_02_owner_roles.sql`.
```
# Import schema
psql vhf < vhf_schema.sql
```

### Import data
The table dumps (`vhf_site.sql`, `vhf_trx.sql`, ...) contain data only and are generated by
`scripts/do_dump.sh`. They disable triggers while loading, so stored values such as the sea level
are kept as they are; run them as the postgres superuser.

A site is defined as location with one or more callsigns and or transceivers. Each active site
contains one or more transmitters and receivers. The settings contain the repeater types offered
by the web page.
```
su postgres
psql vhf -1 -f vhf_site.sql
psql vhf -1 -f vhf_trx.sql
psql vhf -1 -f vhf_bands.sql
psql vhf -1 -f vhf_direct_channels.sql
psql vhf -1 -f bl_kz_prefix.sql
psql vhf -1 -f vhf_setting_options.sql
```

## Setup postgrest
Postgrest is used to provide a REST interface to the database. Its configuration is
`/etc/postgrest/postgrest.conf`, see `postgres/postgrest.conf` for a template.
```
# setup /etc/postgrest/postgrest.conf
# test API
wget https://repeater.oevsv.at/api/site
wget https://repeater.oevsv.at/api/trx
# a more complex query
wget https://repeater.oevsv.at/api/trx?dmr=eq.true&band=eq.2m
```

### Shared secret for logged-in users (JWT)
Without a token every request runs as `web_anon` (the public API above). Logged-in
users of the web page reach PostgREST through the web page's login service
(`repeater-website/auth-service`): it signs a short-lived token (JWT, HS256) per request,
with role `web_user` and the user's `sub` / `callsign`. PostgREST checks the signature with
a secret it shares with the login service, then runs the request as `web_user` with the
token's claims available in SQL (`current_setting('request.jwt.claims', true)`). This is
how `api.user_login()` knows who logged in.

The secret is a random string of at least 32 characters. It must be **identical** in
PostgREST (`jwt-secret`) and in the login service (`PGRST_JWT_SECRET`), and it must not go
into this repository.

```
# 1. Create the secret once, readable only by root and PostgREST.
#    (PostgREST ignores the trailing newline that echo / openssl write.)
openssl rand -hex 32 > /etc/postgrest/jwt-secret
chown root:<user PostgREST runs as> /etc/postgrest/jwt-secret   # see: systemctl cat postgrest
chmod 640 /etc/postgrest/jwt-secret

# 2. PostgREST: in /etc/postgrest/postgrest.conf, load it from that file
#    ("@" = read from file, so the secret is not in the config itself)
jwt-secret = "@/etc/postgrest/jwt-secret"
#    Keep the defaults: jwt-secret-is-base64 = false (the string is the key as it is) and
#    jwt-role-claim-key = ".role" (the token's "role" claim selects the Postgres role).

# 3. Login service: the same value in its environment file /etc/repeater-auth.env
#    (drops an older PGRST_JWT_SECRET line; the leading \n protects against a last
#    line without newline, which would otherwise swallow the new line)
sed -i '/^PGRST_JWT_SECRET=/d' /etc/repeater-auth.env
printf '\nPGRST_JWT_SECRET=%s\n' "$(cat /etc/postgrest/jwt-secret)" >> /etc/repeater-auth.env

# 4. Restart both
systemctl restart postgrest repeater-auth
```

The roles used by the tokens are created by the migrations (`web_user`, granted to
`authenticator`, in `postgres/migrations/2026-11-01_04_users.sql`).

Check:
```
# no token: anonymous, not allowed -> 401
curl -s -X POST http://127.0.0.1:3000/rpc/user_login
# token signed with another secret -> 401 "No suitable key or wrong key type"
# public API unchanged -> 200
curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:3000/rpc/geo?x=16.37&y=48.2'
# then log in on the web page: a row appears / last_seen changes
psql vhf -c 'select callsign, first_seen, last_seen from users order by last_seen desc limit 5'
```
If logins work but no row appears, look at the login service's log
(`journalctl -u repeater-auth -n 50`). After each login it writes one of:

| Log line | Meaning |
|---|---|
| `user_login: OE1ABC <id>, first seen ...` | recorded |
| `user_login skipped: PGRST_JWT_SECRET is not set ...` | the secret doesn't reach the service (env file, restart) |
| `user_login: HTTP 401 ... No suitable key ...` | the two secrets differ |
| `user_login: HTTP 404 ...` | migration `2026-11-01_04_users.sql` not applied |
| `user_login failed: fetch failed` / `... timeout` | PostgREST not reachable at `PGRST_UPSTREAM` |
| nothing at all | the service runs an older `server.js` (redeploy, restart) |

The service's start-up lines also show `jwt-secret set` or `jwt-secret NOT SET`. To check
that both secrets are equal without printing them:
```
tr -d '\n' < /etc/postgrest/jwt-secret | sha256sum
pid=$(systemctl show -p MainPID --value repeater-auth)
tr '\0' '\n' < /proc/$pid/environ | sed -n 's/^PGRST_JWT_SECRET=//p' | tr -d '\n' | sha256sum
```

To change the secret, write a new one to `/etc/postgrest/jwt-secret` and
`/etc/repeater-auth.env` and restart both services; old tokens live only 30 seconds.

## Network links (transmitter ↔ network node)

Each transmitter names the nodes it appears as in the monitored networks, in
`trx.networks` (migration `2026-11-03_04_trx_networks.sql`):

```json
{"oelink": "932832", "ipsc2": "232305", "svx_oe9": "OE9XVV-R", "tetra_oevsv": null}
```

The key is a network from table `network`, the value is the node exactly as
that network lists it (`api.network_node`): repeater ID for OE-LINK and IPSC2,
node with suffix for SVXLink OE9, Tetra ÖVSV (`OE1XCS-T`) and Tetra-DE
(`OE9XFV-R`), station for YCS232, station with module for XLX905 and REF096
(`OE9XGV-B`), device ID for Brandmeister, callsign for DCS009 and ircDDB.
`null` means "this transmitter is not in that network". A trigger rejects unknown networks and a node linked to two transmitters.

Views: `api.trx_network` (one row per link), `api.networks` (per network),
`api.network_unlinked` (work list: listed nodes without a link, with the
candidate transmitters). The website shows them on `/networks`.

### Automatic fill

```
psql vhf -f postgres/scripts/trx_networks_autofill.sql              # dry run
psql vhf -v apply=1 -f postgres/scripts/trx_networks_autofill.sql   # link
```

Rules, in this order: same `digital_id` (OE-LINK, IPSC2, Brandmeister); for
D-STAR module nodes (`OE6XDF-B`) the transmitter with that `dstar_rpt1`; same
callsign and the frequency the node reports (SVXLink OE9, Tetra ÖVSV,
Tetra-DE, Brandmeister); for networks of one mode only, the callsign alone
if it has exactly one active transmitter of that mode. Mixed networks (FM + TETRA) never link by callsign alone. Anything
ambiguous is left for manual linking. Running it again is safe: it only adds
links for nodes and transmitters without one and never changes a key that is
already set (also not a `null`), so manual corrections survive.

### Manual corrections

```sql
-- what is left, with candidates
SELECT network_id, node, callsign, node_frequency, candidates FROM api.network_unlinked ORDER BY 1, 2;

-- link a node to a transmitter (uid from the candidates)
UPDATE trx SET networks = networks || '{"svx_oe9": "OE7XLH-R"}' WHERE uid = 2170;

-- move a wrong link: remove it from one transmitter, add it to the other
UPDATE trx SET networks = networks - 'tetra_oevsv' WHERE uid = 2406;
UPDATE trx SET networks = networks || '{"tetra_oevsv": "OE1XCS-R"}' WHERE uid = 2423;

-- this transmitter is not in that network: the automatic fill leaves it alone
UPDATE trx SET networks = networks || '{"svx_oe9": null}' WHERE uid = 2180;

-- remove a link (the automatic fill may add it again; use null to prevent that)
UPDATE trx SET networks = networks - 'svx_oe9' WHERE uid = 2180;
```

New network: add a row to `network`, a scraper, and its nodes to the view
`api.network_node`.
